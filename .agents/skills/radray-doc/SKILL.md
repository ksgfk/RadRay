# RadRay 文档维护

在包含 RadRay 根 `AGENTS.md` 的仓库工作。先读该文件和 `docs/architecture/overview.md`，
再按本次任务读取所属文档及其代码锚点；通常按需读取，用户要求通读或全面审计时覆盖指定范围。
本技能中的路径均相对仓库根解析，需要时通过文件工具读取；技能正文不使用 Markdown 文件链接、
机器绝对路径或跨目录的 `../` 链接来引用仓库文档。

## 硬约束：当前文档只记录事实

- `docs/architecture/`、`docs/guide/` **只能记录当前代码库可核实的事实**：已实现行为、接口契约、
  当前配置、已有测试覆盖、可执行操作，以及根 AGENTS 和仓库现行开发规则。说明设计理由时必须对应现有实现。
- **禁止**在这两个目录保存计划、路线图、待办、提案、目标设计、备选方案、实施清单、
  推测或「已确认、未实现」段落。用户确认了方案也不等于代码已经实现；加状态标签不能豁免此约束。
- 任何需要落盘的计划、未实施结论、实验过程或验收记录都只能放在 `docs/history/`，并遵守下文的保存授权规则。
  未授权保存时留在会话；不得为了保留内容将其塞入当前文档。当前能力缺口可以按源码写成事实，不附带未来实现安排。
- 逐项对照当前声明、实现、构建配置和测试；发现不符就修正，无法核实或已失效就删除。
  历史报告、旧测试结果和外部 checkout 不能单独证明当前代码库的行为或覆盖。

## 归属

- 根 `AGENTS.md` 也是文档：只保留跨模块硬约束、必要工作规则和少量入口。改动须遵守当前用户授权，不借整理之名改变工程规则。
- `docs/architecture/` 描述已实现的结构、接口契约、生命周期、术语及必要设计理由。优先改所属子系统文档，overview 只做当前地图和入口。
- `docs/guide/` 描述当前可执行的操作、编写和验证方法。调整文档组织时，从仓库根读取 `docs/guide/documentation.md`。
- `docs/history/` 保存经用户授权保留的计划和开发历史，包括设计快照、实验、验收和交接。注明状态、适用范围和基线提交，不作为当前技术契约。
- `docs/history/README.md` 单独维护历史目录索引，按需读取；overview 只链接这一入口，不展开历史条目。索引是可更新的导航文件，不属于冻结的历史记录，不加日期前缀。
- README 只保留项目介绍与入口；项目技能放 `.agents/skills/`。不修改用户全局技能或配置。
- 不另建全局词汇表、编号决策记录、研究档案或计划目录。未经用户授权保存的讨论过程、备选草案和日志留在会话。

## 更新方式

1. 查当前工作树和引用，以实际实现核实当前事实。用户确认但未落地的决定仅按历史保存规则处理，不写入 architecture/guide。
2. 在所属文档中就地更新；同一事实只维护一处，其余使用链接。术语在首次使用处解释，设计理由只保留足以避免误改的原因和代价。
3. 删除或合并文档前检查引用和独有内容。核对仍适用的内容后迁入所属文档，淘汰过时内容；不要把旧文件整包搬进 architecture 冒充整理。
4. 新建 docs 页面时使用 `适用`、`权威`、`锚点` 三行头部，锚点填写存在的仓库相对路径。根 AGENTS、README 和 SKILL 不套这个头部。
5. docs 页面引用代码时使用仓库相对锚点和 Markdown 相对链接；技能正文遵守上面的路径读取规则。
   外部规范仅用于解释现有实现的契约，在实际需要的段落给出一手来源及版本，不自动生成研究报告。
6. 改页面归属、入口或工程规则时同步相关索引、README、AGENTS 和技能引用；不要复制一份规则进每个入口。

## 开发历史

默认不新增历史记录。实现、重构、修复、测试通过或整理文档本身都不构成写入历史的授权。
AI 认为内容有复用或追溯价值时，可以主动询问是否录入 history，简述拟记录的内容与保留理由；不必每次改动都询问。
用户明确要求或同意保存后才写入；已有授权直接执行，不重复确认。未回复或未明确同意时保留在会话，不阻塞其他已授权工作。
「更新文档」「带文档 grill」默认只同步已核实的当前事实，不自动追加历史。
用户明确要求保存计划或未实施设计结论时，按该授权写入 history，不重复询问；实施后再根据实际代码更新当前文档。
已有 `docs/history/` 记录与附件保持原样，不修改、补注、改名或删除；不因实现演进、文档整理或检查报错回写正文、链接和锚点。
与历史相比的行为、API、约束或验证范围变化，只在当前所属的 architecture/guide 页面说明；
仅保留理解现状所需的事实，必要时链接原记录，不复制历史全文或累积开发日志。新增记录后更新 `docs/history/README.md`。

历史文档与附件使用 `YYYY-MM-DD-主题.扩展名`；归档时从仓库根读取 `docs/guide/documentation.md` 的「开发历史」章节，
按其中的日期选择、附件命名和归档边界执行。`docs/history/README.md` 仅作索引，是日期命名的唯一例外。

删除或重构子系统前，若用户明确要求或同意保存现有设计，先在 history 写明职责、依赖、数据流、所有权、
线程/帧生命周期、关键约束和限制，并记录删除前的 Git 提交。旧源码路径放在正文中，配合
`git show <基线>:<路径>` 查阅；新增记录时核对头部锚点，后续路径变化不回写历史。必要时保留标明基线的旧文档附件。
实现后只同步当前长期文档与索引；仍适用的结论和必要的前后差异写在所属当前页面，历史快照不改。

## 完成检查

从仓库根运行 `python tools/check_docs.py` 和 `git diff --check`。
检查当前文档中的命令、类型名、配置开关与当前文件一致；历史内容按其基线理解。
检查器不按当前工作树校验历史记录内的文档引用、源码锚点和本地链接；仍检查历史页面头部与文件命名。
`docs/history/README.md` 的头部、锚点和链接按当前文档严格校验。逐段确认 architecture/guide 没有计划、未实施结论或无法核实的断言；检查器不能替代事实核对。
当前文档、入口、技能和源码中的引用继续严格校验，包括它们指向 history 的链接。不为通过检查回写历史。
修改检查脚本时验证能发现缺失引用。
纯文档修改不要求编译 C++。汇报改动与实际执行的检查，不把旧测试记录写成此次验证。
