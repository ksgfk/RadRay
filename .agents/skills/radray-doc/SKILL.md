# RadRay 文档维护

在包含 RadRay 根 `AGENTS.md` 的仓库工作。先读该文件和 `docs/architecture/overview.md`，
再按本次任务读取所属文档及其代码锚点；不要遍历加载整个文档树。

## 归属

- 根 `AGENTS.md` 也是文档：只保留跨模块硬约束、必要工作规则和少量入口。改动须遵守当前用户授权，不借整理之名改变工程规则。
- `docs/architecture/` 描述当前结构、接口契约、生命周期、术语及必要设计理由。优先改所属子系统文档，overview 只做地图。
- `docs/guide/` 描述如何操作、编写和验证。文档维护规范在 `docs/guide/documentation.md`，需要调整文档组织时读取。
- `docs/history/` 保存经用户授权保留的开发历史，包括设计快照、实验、验收和交接。注明状态、适用范围和基线提交，不作为当前技术契约。
- README 只保留项目介绍与入口；项目技能放 `.agents/skills/`。不修改用户全局技能或配置。
- 不另建全局词汇表、编号决策记录、研究档案或计划目录。未经用户授权保存的讨论过程、备选草案和日志留在会话。

## 更新方式

1. 查当前工作树和引用。以实际实现说明现状，以用户明确确认的决定说明目标；发现不一致就明确区分，不把计划写成已实现。
2. 在所属文档中就地更新；同一事实只维护一处，其余使用链接。术语在首次使用处解释，设计理由只保留足以避免误改的原因和代价。
3. 删除或合并文档前检查引用和独有内容。核对仍适用的内容后迁入所属文档，淘汰过时内容；不要把旧文件整包搬进 architecture 冒充整理。
4. 新建 docs 页面时使用 `适用`、`权威`、`锚点` 三行头部，锚点填写存在的仓库相对路径。根 AGENTS、README 和 SKILL 不套这个头部。
5. 文档引用代码，使用仓库相对锚点和 Markdown 相对链接。涉及外部证据时只在实际需要的段落给出一手来源及版本，不自动生成研究报告。
6. 改页面归属、入口或工程规则时同步相关索引、README、AGENTS 和技能引用；不要复制一份规则进每个入口。

已确认但尚未实施的决定，只有在用户要求保存设计结论时才写入所属页面的简短「已确认、未实现」段落，
明确适用范围和与当前行为的差异。落地时改正文并移除该段，不积累时间线。

## 开发历史

默认不新增历史记录。实现、重构、修复、测试通过或整理文档本身都不构成写入历史的授权。
AI 认为内容有复用或追溯价值时，可以主动询问是否录入 history，简述拟记录的内容与保留理由；不必每次改动都询问。
用户明确要求或同意保存后才写入；已有授权直接执行，不重复确认。未回复或未明确同意时保留在会话，不阻塞其他已授权工作。
「更新文档」「带文档 grill」默认更新所属长期页面，不自动追加历史。已有记录可按用户授权的整理或修正范围维护。

历史文档与附件使用 `YYYY-MM-DD-主题.扩展名`；日期选择、附件命名和归档边界见
[文档维护](../../../docs/guide/documentation.md#开发历史)。用户明确指定其他保存位置时遵循其请求。

删除或重构子系统前，若用户明确要求或同意保存现有设计，先在 history 写明职责、依赖、数据流、所有权、
线程/帧生命周期、关键约束和限制，并记录删除前的 Git 提交。旧源码路径放在正文中，配合
`git show <基线>:<路径>` 查阅；头部锚点仍指向当前存在的仓库文件。必要时保留标明基线的旧文档附件。
实现后同步长期文档，历史快照保留当时语义；仅将确认且仍适用的结论归并到所属长期页面，并在历史入口链接过去。

## 完成检查

从仓库根运行 `python tools/check_docs.py` 和 `git diff --check`。
检查文档中的命令、类型名、配置开关与当前文件一致；修改检查脚本时验证能发现缺失引用。
纯文档修改不要求编译 C++。汇报改动与实际执行的检查，不把旧测试记录写成此次验证。
