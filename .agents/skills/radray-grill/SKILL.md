# RadRay 设计追问

先读根 `AGENTS.md`，从 `docs/architecture/overview.md` 找到本次主题的所属文档。
仅核查相关接口、实现和测试。项目中的术语与设计理由都在所属 architecture/guide 页面，
不依赖全局技能、独立词汇表或历史会话作为当前契约。

## 追问

- 根据用户目标列出关键决策及前置关系，区分已确认、待决、待查事实；这份工作记录留在会话。
- 先追问一个最能影响后续设计的问题，给出推荐选择、原因、实际代价或反例，再等待回答。
  不把依赖未决前提的问题提前塞给用户；用户明确要求一轮多问时可合并相互独立的问题。
- 文件、代码行为和构建边界等可查事实由自己核实，不让用户代查。证据不足时说明未知，
  只询问会改变设计的偏好与约束；不默认启动子代理或展开外部研究。
- 用户回答后更新决策关系。用具体场景核验，例如资产引用释放而 GPU 仍在使用、flight 复用、
  JIT 关闭、双后端差异；只选与当前主题相关的场景，不强制套完整检查清单。
- 发现术语歧义、代码与假设矛盾时指出具体位置，确认用户是在描述现状还是要求改变它。
- 已解决的分支不反复追问。没有影响范围、正确性或验收的未决问题后，给出简短的共享理解：
  目标、已确认选择、边界、实现与验收条件，然后请用户确认。

## 从讨论到落地

追问期间可只读探索；开始实现需用户确认共享理解。用户已经明确确认并要求实施时直接继续，
不再次索要同一许可；普通实现任务不因自动匹配此技能而退回访谈。

默认把讨论结果留在会话。用户要求「带文档 grill」或保存已确认决定时，读取相邻的
[radray-doc](../radray-doc/SKILL.md)，更新所属长期文档；未实施结论明确标注，不能覆盖当前事实。
不因一个术语刚明确就创建文件，也不生成 ADR、独立 CONTEXT、研究档案或实施清单。
更新文档后运行项目文档检查。用户中途改方向时保留仍有效的决定，重新追问受影响的分支。
