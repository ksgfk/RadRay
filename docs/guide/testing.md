# 编写测试

测试描述模块对外承诺的行为。读测试的人应当能从用例名和断言看出“这个模块做什么”，
而不是“这个实现内部怎样走”。构建、夹具准备与 CTest 命令见[构建与测试](build-test.md#测试)。

## 测什么

- 公共接口的可观察结果：返回值、输出数据、对象状态、GPU 读回内容。
- 文档写明的错误契约：返回错误、空值或 `false` 的输入。只测接口承诺会拒绝的输入，
  不向接口提交违反前置条件的调用，也不断言 Debug 断言或未定义行为。
- 曾经出过错的边界：空输入、容量增长、对齐、首尾元素、跨后端差异。每个边界一条用例。
- 容易回归的组合：只在两个特性确实相互影响时才写组合用例，不做笛卡尔积。

## 不测什么

- 内部计数、调用次数、调用顺序与缓存命中次数，除非它们就是接口契约。
- 原生 API、驱动、编译器或第三方库本身的行为；例如 DXC 的具体输出字节、validation 消息条数。
- 类型系统已经保证的事，例如对显而易见的类型特征逐个 `static_assert`。
- 日志与错误消息的完整文本；需要时只检查关键字段。
- 只为测试才存在的生产代码字段或开关。观测数据由测试自己的 fake、probe 或 fixture 持有（见 AGENTS 硬规则）。

## 用例形态

- 一条用例只验证一个行为。名称写成 `Suite.行为描述`，例如 `SparseSet.EraseKeepsOtherElementsReachable`。
- 按准备、执行、断言三段书写；断言只覆盖该行为需要的事实。
- 前置失败会让后续断言失去意义时用 `ASSERT_*`，其余用 `EXPECT_*`。
- 优先使用内联的小数据；只有输入本身是文件格式（OBJ、PNG、HLSL）时才放到 `tests/data/`。
- 参数化只用于同一行为在多个后端、类型或格式上成立的情况；参数名应能在测试名里读懂。
- 辅助函数服务于可读性。fixture 和工具代码不应比它支撑的用例更复杂。
- 依赖用 fake 替代，直接实现被依赖的接口并记录测试关心的少量事实；不引入 mock 框架。

## GPU 测试

render 测试链接进 `test_radray_render`，共用 [gpu_test_fixture.h](../../modules/render/tests/gpu_test_fixture.h)：

- 每个后端各实例化一次（参数 `D3D12`、`Vulkan`）。后端未编译或没有可用设备时跳过；
  `RADRAY_TEST_REQUIRED_BACKENDS=d3d12,vulkan` 把跳过变为失败。
- 设备默认开启原生 validation 与 RHI validation，用例结束时出现 validation 错误即失败。
  `RADRAY_TEST_GPU_VALIDATION=1` 额外开启 GPU-assisted validation。
- 结果以读回内容为准：写入已知图案，提交并等待完成，再逐元素比较。
- 可选能力（例如外部资源、特定格式）先查询；查询不支持时跳过，查询支持后任何失败都是失败。
- shader 使用 `RADRAY_TEST_SHADER_DIR` 下预生成的字节码，运行时不依赖 DXC。

## TDD 流程

新功能与缺陷修复按“红—绿—重构”推进：

1. 先写一条描述目标行为的用例，构建并确认它因为目标行为缺失而失败。
   缺陷修复的第一步是写出能复现缺陷的用例。
2. 写出让这条用例通过的最小实现，不顺带实现尚无用例的行为。
3. 在全部用例保持通过的前提下整理实现和测试代码。
4. 重复以上步骤，直到行为完整。提交前运行所属模块的全部用例。

接口尚未稳定时，先用一两条用例确定调用方式，再补边界与错误路径。
发现现有实现与文档契约不一致时，按文档写用例并报告差异，不为了通过测试修改断言。
