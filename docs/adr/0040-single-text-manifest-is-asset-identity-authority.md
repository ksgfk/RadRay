# ADR-0040 单文本 JSON 清单是资产身份权威

状态: 部分被 ADR-0050 取代
日期: 2026-08
影响: `modules/runtime` 的 `AssetDatabase`、asset 身份与元数据的持久形态、`third_party/`
依赖（移除 LMDB）与 `project_manifest.json`；取代 ADR-0038

## 背景

ADR-0038 把 asset 元数据的唯一权威定为 LMDB 的 `assets` 表，XML 降级为落盘快照；ADR-0039 又
放弃 per-bundle 组织，于是 XML 落盘形态一并搁置，实现落成"纯临时 LMDB 工作库、无任何持久
文本"。这个组合有两个此前未被称重的缺陷：

1. **GUID 跨机器不稳定。** GUID 是永久身份（ADR-0036），一旦被引用方写下（材质引用贴图、
   场景引用 mesh），它就必须在任意克隆、任意机器上指向同一份资产。而 LMDB 单文件是本地
   产物：另一台机器克隆仓库后对同一个源文件重新 `AddEntry` 会分配不同 GUID，全部既有引用
   当场失效。身份权威必须与源文件一同进版本控制。
2. **二进制权威与 merge 动机正面冲突。** ADR-0036 选 XML 的唯一动机是 merge 冲突集中易解；
   ADR-0038 用一个不可合并的二进制文件取代它当权威，把那条动机整个丢掉了。两人各加一个
   资产就是不可解冲突。

同时 ADR-0039 已确认当前阶段目标是"稳定 asset 系统"，而 `AssetDatabase` 在两轮之后仍然零
消费方（sample 不加载资产、`AssetManager::Load` 的唯一调用方是测试）。必须决定身份与元数据
究竟持久在哪里，且这次要有真实消费方压着它。

## 决策

**asset 身份与元数据的唯一权威是一份进版本控制的 JSON 文本清单；不再有本地数据库。**

- 一个资产根 = 一份清单，固定位于 `<AssetRoot>/assets.json`。`AssetDatabase` 载入时把它
  全量读进内存的普通 C++ 结构（`AssetEntry`），运行时查询是纯内存查表。
- **资产根由装配方传入**（`ApplicationRuntimeDescriptor::AssetRoot`），代码里不出现任何
  硬编码路径。本仓库是引擎根而非游戏项目根，`assets/` 只是引擎自带的样例与测试资产；
  游戏项目传自己的资产根，引擎侧零改动。清单文件名相对资产根固定，故搬动资产目录不需要
  改代码。
- 条目字段：`guid`（永久身份）、`path`（资产根相对、可变元数据）、`type`（importer 键）、
  可选 `settings`（导入设置，形状见 ADR-0042）。
- **双索引**：`AssetId → 条目` 与 `path → AssetId`（大小写不敏感）。path 反查是人类可用的
  唯一入口——没有它，调用方只能手抄 GUID，这正是前两轮 `AssetDatabase` 零消费方的直接原因。
- **落盘 = 按 path 排序的全量重写**，不保序、不保注释（JSON 无注释）。排序让条目在文件中的
  位置稳定：两人各加一个资产时冲突要么不发生，要么是"两侧都保留"的平凡形态。
- 格式选 JSON 而非 XML：`radray/json.h`（yyjson 封装）已提供 `JsonSerializer` /
  `JsonDeserializer` 双向定制点，无需新依赖；XML 当初被选中的唯一理由（保序 merge）在
  ADR-0038 已被推翻，不再成立。
- **`Open` 失败不抛异常**：返回 `unique_ptr` + `string& outError`（纠正 ADR-0038 落地时
  引入的 `std::runtime_error` 构造，那违反仓库异常规则）。
- **移除 LMDB 依赖**，连同 `radray/lmdb.h` 封装一并撤出。

保留自 ADR-0036 的身份规则不变：GUID 由 `AddEntry` 一次分配、任何代码路径都不得改变它；
移动/重命名 = 改 `path`；AssetId 双轨并存（入库 GUID + 散文件 `MakeAssetIdFromPath`）互不迁移。

## 放弃的方案及代价

- **LMDB 作唯一权威（ADR-0038）**：读取快、事务成熟，但 GUID 只诞生于本地库因而跨克隆
  不稳定，且二进制文件不可合并——两个缺陷都直接打在"身份"这个它承担的职责上。存储性能
  在开发时清单（量级：百到千条）上不是瓶颈，用它换正确性是错的取舍。
- **LMDB 作缓存 + 文本清单作权威**：正确性没问题（删库重扫结果一致），但当前规模下缓存
  层没有可测收益，纯增一层同步逻辑与一个第三方依赖。规模真成问题时再加，届时权威已经
  在正确的地方。
- **per-file `.meta`（Unity 式）**：GUID 跟着源文件走，移动文件天然保住身份，冲突隔离到
  单文件——这是最强形态。代价是文件数翻倍、资产目录被元数据污染、且移动资产必须同时移动
  两个文件（漏一个就静默丢身份）。当前资产量级不值得，但这是清单文件涨到不可维护时的
  首选演进方向，`version` 字段为此预留。
- **XML 单清单**：`radray/xml.h` 现成，但保序动机已废，剩下的只是比 JSON 更啰嗦的语法；
  且 pugixml DOM 句柄会把生命周期约束重新引进公开签名（见 ADR-0042）。
- **继续无持久文本（ADR-0039 落地态）**：最省事，但每次运行 GUID 重新分配，等于没有身份，
  跨资产引用无从建立。

## 必须保持为真

- asset 身份与元数据的唯一权威是 `<AssetRoot>/assets.json`；不存在任何本地数据库或缓存
  参与身份分配。
- 代码中不出现硬编码的资产根路径或清单文件名以外的约定；资产根一律由装配方传入。
- GUID 只在 `AddEntry` 时 `Guid::NewGuid()` 一次分配。移动、重命名、`Refresh` 重扫、
  清单重写都不得改变已有 GUID；`Refresh` 发现清单条目对应文件缺失时保留条目与 GUID。
- GUID 文本写出固定 `Guid::ToString()` 的 D 格式小写；读取走 `Guid::TryParse`（宽容
  N/D/B/P）。**禁用会抛异常的 `Guid::Parse`**。
- `path` 是资产根相对、`/` 分隔、词法规范化的路径，唯一性按大小写不敏感口径校验。
- 清单落盘是按 `path` 排序的全量重写；不承诺保序或保留任何非条目内容。
- `AssetDatabase` 同时提供 `AssetId` 与 `path` 两条查询入口。
- 构造失败经返回值与 `outError` 表达，不抛异常。
- 仓库不依赖 LMDB。
